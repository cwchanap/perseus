# Puzzle Difficulty, Achievements, and Leaderboards Design

Date: 2026-08-26

Freshness review: revised against `main` at `67be5f3e28ab78c186e100e53cd09c6dc7f37f57` after the NativeScript offline-library and Access-only admin changes landed.

## Summary

Perseus currently treats each server puzzle as one concrete generated board with one piece count. This design replaces that server catalog model with a player-facing **puzzle family** that owns one image and exactly three concrete **puzzle variants**: Easy, Normal, and Hard.

A variant remains the gameplay identity. It has one puzzle ID, one fixed grid, generated pieces, saved progress, completion runs, local stats, and competitive best times. `PuzzleSession` continues to understand only one concrete board and never gains mutable difficulty state.

A family becomes the catalog, ownership, shared-image, workflow, deletion, and reaper identity. This distinction is important because the three variants share an original image and thumbnail and are generated by one Cloudflare Workflow.

The same cutover also adds fixed global achievements, non-scoring per-variant mastery, Standard/Rotation time leaderboards per difficulty, and an overall score derived from unique family+difficulty completions plus achievement rows.

The change is intentionally breaking. Old arbitrary-count server puzzles are regenerated as new families; old server saves and completion history are not translated into the new difficulty semantics. Quick Puzzles remain local and unchanged.

## Goals

- Make every server puzzle available at Easy, Normal, and Hard difficulty.
- Define difficulty only by piece count/grid size.
- Preserve the invariant that one puzzle ID identifies one immutable board geometry.
- Keep family/catalog lifecycle separate from variant/gameplay lifecycle.
- Generate all three variants eagerly in one Workflow with retry-safe checkpoints.
- Add replay value without repeat-completion farming.
- Add Standard and Rotation competitive time boards per family+difficulty.
- Add an overall ranking driven primarily by unique clears, with small one-time achievement bonuses.
- Preserve the shipped profile Puzzle Results screen under the new family+difficulty model.
- Move both web and NativeScript catalog clients to the family API in the same cutover.
- Reuse the current Access-only admin model and existing `PUZZLE_METADATA_DO` binding.
- Keep local Quick Puzzles independent from server families/progression.

## Non-goals

The first release does not add:

- daily/weekly/monthly leaderboards or seasons
- streaks or recurring quests
- configurable achievement rules or an achievement DSL
- XP/levels separate from leaderboard score
- currencies or unlock rewards
- category-completion achievements
- arbitrary solve-time achievements
- mastery score
- assisted or relaxed time leaderboards
- country/friends-only rankings
- live/WebSocket leaderboard updates
- anti-cheat machinery
- percentile calculations
- a second metadata Durable Object binding
- child workflows or a workflow coordinator
- a mutable score ledger or materialized overall leaderboard
- a generic rankings/progression framework
- runtime V1 completion parsing
- a `legacy` difficulty
- runtime compatibility branches for old server catalog/save formats

## 1. Difficulty Model

Difficulty is piece count only.

| Difficulty | 1:1 | 4:3 | 3:4 |
| --- | ---: | ---: | ---: |
| Easy | 4x4 = 16 | 4x3 = 12 | 3x4 = 12 |
| Normal | 7x7 = 49 | 8x6 = 48 | 6x8 = 48 |
| Hard | 10x10 = 100 | 12x9 = 108 | 9x12 = 108 |

The values live in `@perseus/types` and every value must satisfy the existing `isValidPieceCountForAspectRatio`/`getGridDimensionsForAspectRatio` rules.

Conceptually:

```ts
export const PUZZLE_DIFFICULTIES = ['easy', 'normal', 'hard'] as const;
export type PuzzleDifficulty = (typeof PUZZLE_DIFFICULTIES)[number];

export const DIFFICULTY_PIECE_COUNTS = {
  easy: { '1:1': 16, '4:3': 12, '3:4': 12 },
  normal: { '1:1': 49, '4:3': 48, '3:4': 48 },
  hard: { '1:1': 100, '4:3': 108, '3:4': 108 }
} as const;
```

Do not store difficulty configuration in D1 or make it admin-editable.

Rotation, hints, reference modes, and timed/relaxed mode keep their current independent semantics. Easy does not automatically disable rotation or enable assistance, and Hard does not force rotation.

## 2. Family and Variant Model

### 2.1 Puzzle family

A family is the player-facing identity of one uploaded image:

```ts
interface PuzzleFamilyMetadata {
  id: string;
  name: string;
  category?: PuzzleCategory;
  aspectRatio: PuzzleAspectRatio;
  createdAt: number;
  status: 'processing' | 'ready' | 'failed';
  variants: Record<PuzzleDifficulty, string>;
}
```

The family owns:

- name/category/owner
- aspect ratio
- original image
- thumbnail
- three preallocated variant IDs
- family workflow/status
- gallery/admin/mobile catalog identity
- family deletion/reaper lifecycle

The three variant IDs are allocated once at family creation and reused by retries.

### 2.2 Puzzle variant

A variant is one concrete playable board. Existing puzzle metadata gains immutable family identity:

```ts
familyId: string;
difficulty: PuzzleDifficulty;
```

A variant owns:

- piece count
- grid rows/columns
- piece metadata/assets
- saved session
- local stats
- completion runs
- Standard/Rotation best times
- per-variant mastery

### 2.3 Gameplay boundary

`PuzzleSession` stays variant-based and receives one concrete `puzzleId`, `pieceCount`, `gridRows`, `gridCols`, and piece list.

Do not add difficulty to session setup and do not key a session by `familyId + difficulty`. Family+difficulty is resolved to a variant ID before gameplay starts.

## 3. Metadata and Asset Ownership

### 3.1 KV/DO read models

Use separate KV keys:

```text
family:<familyId>        -> family read model
puzzle:<variantId>       -> variant read model
```

Reuse the existing `PUZZLE_METADATA_DO` namespace as the only strong-consistency binding. Address the same DO class by family ID for family mutations and by variant ID for variant mutations. Generalize the stored entity/update contract with a `family | variant` discriminator; do not add another DO namespace.

KV remains the public/listing read model synced from authoritative DO writes.

### 3.2 Family readiness

```text
all three variants ready -> family ready
any terminal variant failure -> family failed
otherwise -> family processing
```

The public gallery lists `family:*` records only. Variants never appear as independent catalog cards.

### 3.3 R2 layout

```text
families/<familyId>/original
families/<familyId>/thumbnail.jpg

puzzles/<variantId>/pieces/0.png
puzzles/<variantId>/pieces/1.png
...
```

Variant reference-image reads resolve `variantId -> familyId` and serve the family original. Family catalog/admin/mobile thumbnails use the family thumbnail.

There is no variant-owned original or thumbnail after cutover.

## 4. D1 Catalog and Progression Schema

Replace the old standalone `puzzles` ownership mirror with:

```text
puzzle_families
  id                 PK
  owner_id
  name
  category           nullable
  aspect_ratio
  status
  created_at

puzzle_variants
  id                 PK
  family_id
  difficulty
  piece_count
```

`(family_id, difficulty)` is unique.

D1 remains a query/ownership/progression store; KV/DO remains authoritative for live processing metadata.

Profile summary semantics become:

- `puzzlesUploaded`: owned families
- `puzzlesSolved`: distinct families with at least one completed difficulty
- `totalCompletions`: accepted completion runs across variants, including replays

The destructive migration drops `timingQuality` / `legacy_unknown`; no compatibility column survives the reset.

## 5. Family-Scoped Deletion and Reaping

Family is the only catalog/deletion/reaper grain. A variant must never be independently reaped or exposed through an admin delete action.

This is required because the three variants share family R2 assets and because `family.variants` must never point at a sibling that was independently tombstoned.

### 5.1 Cleanup record

Replace puzzle-scoped cleanup state with a family-scoped record containing enough immutable data to retry cleanup without rereading mutable catalog state:

```ts
interface CleanupRecord {
  familyId: string;
  variantIds: Record<PuzzleDifficulty, string>;
  pieceCounts: Record<PuzzleDifficulty, number>;
  idempotencyKey?: string;
  createdAt: number;
}
```

### 5.2 Reaper

The stuck-workflow reaper scans `family:*`, checks the family workflow/authoritative family status, and decides cleanup once for the whole family. It never scans `puzzle:*` variants as independent workflow owners.

### 5.3 Existing completion deletion fence reuse

Completion submissions are still addressed by variant ID, so reuse the current `CompletionWriteExecutor` deletion fence once per variant ID:

```text
family cleanup chosen
  -> persist family CleanupRecord
  -> beginPuzzleDeletion(easyVariantId)
  -> beginPuzzleDeletion(normalVariantId)
  -> beginPuzzleDeletion(hardVariantId)
  -> tombstone family + variant metadata DOs
  -> delete family original/thumbnail
  -> delete three variant piece sets
  -> remove family + variant KV/D1 catalog rows
  -> finishPuzzleDeletion() for each variant
  -> delete cleanup record
```

Do not introduce a second deletion protocol. The family orchestration wraps the existing per-variant completion fence.

`finishPuzzleDeletion()`/family cleanup removes family-scoped runs, best times, first-clear rows, and mastery for the deleted family while maintaining retained-run usage. Global achievement rows remain unlocked; achievements are monotonic account milestones and are not recomputed/revoked when content is later deleted.

## 6. Upload and One-Workflow Generation

Server uploads accept:

- image
- name
- optional category
- aspect ratio

They no longer accept an arbitrary server `pieceCount`.

Creation:

```text
upload image
  -> allocate family ID
  -> allocate Easy/Normal/Hard variant IDs
  -> store family original
  -> create family + ownership rows
  -> start Workflow id = familyId
       -> generate family thumbnail once
       -> generate Easy rows
       -> finalize Easy
       -> generate Normal rows
       -> finalize Normal
       -> generate Hard rows
       -> finalize Hard
       -> finalize family ready
```

### 6.1 Workflow checkpoint names

Cloudflare Workflow step names must be unique within one family instance. Every repeated step inside the difficulty loop is difficulty-qualified:

```text
generate-easy-row-0
generate-easy-row-1
...
finalize-easy

generate-normal-row-0
...
finalize-normal

generate-hard-row-0
...
finalize-hard

finalize-family
```

Any D1/status mirror or retry checkpoint repeated per difficulty follows the same rule. Do not reuse `generate-row-${row}` or one shared `finalize` inside the loop, and do not collapse all variants into one coarse step. Row checkpoints remain the retry unit.

### 6.2 Failure behavior

If a variant reaches terminal generation failure:

- family becomes failed
- shared original remains
- already generated sibling assets remain
- retries reuse the preallocated IDs and difficulty-qualified checkpoints
- family never appears in the playable gallery until all three variants are ready

## 7. Public and Admin API Surface

### 7.1 Public family/catalog APIs

```text
GET  /api/puzzle-families
GET  /api/puzzle-families/:familyId
POST /api/puzzle-families             # signed-in player upload
GET  /api/puzzle-families/:familyId/thumbnail
```

Family summary/detail returns the three variant summaries with `id`, `difficulty`, and `pieceCount`.

### 7.2 Concrete gameplay APIs

```text
GET  /api/puzzles/:variantId
GET  /api/puzzles/:variantId/reference
GET  /api/puzzles/:variantId/pieces/:pieceId/image
POST /api/puzzles/:variantId/complete
```

There is no public `GET /api/puzzles` catalog list after cutover. This prevents the web/mobile clients from drifting onto two catalog models.

### 7.3 Admin API and Cloudflare Access

Rename the admin list/create collection consistently to:

```text
GET  /api/admin/puzzle-families
POST /api/admin/puzzle-families
```

Update the narrow CLI Access application from exact `/api/admin/puzzles` to exact `/api/admin/puzzle-families`, including Pulumi tests and CLI token URL helpers. Do not keep the old path as a compatibility alias.

Family deletion stays browser-admin-only under the broad `/api/admin/*` Access policy and deletes one whole family, never one variant.

Admin remains Access-only; this feature does not reintroduce passkeys or app-level admin authentication.

## 8. Web Gallery, Saves, and Local Stats

### 8.1 Family card

A family card is not one playable link. It renders the shared image/name/category and three difficulty actions. Each difficulty action resolves one variant ID.

Each difficulty action owns its own display state:

```text
Easy · 16 pieces · PLAY
Normal · 49 pieces · CONTINUE 12/49 · ◆ 08:42
Hard · 100 pieces · PLAY
```

There is no single family `pieceCount`, single family `placedCount`, or single family local best.

### 8.2 Saved progress

Session storage remains concrete-variant keyed.

New server variants use:

```text
puzzle-progress-v2-<variantId>
```

Quick Puzzle IDs retain their current keys:

```text
puzzle-progress-q-<...>
```

Old server `puzzle-progress-<uuid>` saves are intentionally ignored.

`galleryProgress` continues to discover/validate concrete session IDs. For a visible family it resolves progress independently for the three variant IDs. Off-page discovery still fetches concrete variant detail when needed and maps the result back to family name+difficulty for display.

If multiple difficulties have resumable saves, each difficulty shows its own Continue state; do not choose a single ambiguous family Continue target.

### 8.3 Local stats

Local statistics stay keyed by concrete variant ID (`puzzle-stats-<variantId>`). The existing local card best remains the Standard timed best for that variant. Rotation competition is represented by the server leaderboard, not by merging modes into the local card best.

No family-level local stats aggregate is added.

## 9. Completion V2 Ownership

`SealedCompletion` already owns the immutable completion facts. The canonical projection helper in `@perseus/game-core` becomes V2:

```ts
completionRequestFromSeal(seal): RecordPuzzleCompletionV2
```

It emits exactly:

```ts
{
  version: 2,
  runId: seal.runId,
  resultClass: seal.resultClass,
  elapsedActiveSeconds: seal.elapsedActiveSeconds,
  hintsUsed: seal.hintsUsed,
  incorrectAttempts: seal.incorrectAttempts
}
```

The Svelte route calls this helper; it does not hand-assemble V2.

The server derives `familyId` and `difficulty` from trusted variant metadata. The client never submits family, difficulty, or score.

`rotationEnabled`/`rotationUsed` are not duplicated into the server payload because the initial server rules need only `resultClass === 'rotation_timed'` for Rotation Clear.

## 10. Completion Transaction and Replay Equality

Extend the existing `CompletionWriteExecutor.write()` transaction; do not add a parallel progression transaction/service.

The trusted input includes server-derived identity plus V2 facts:

```ts
interface VersionedCompletionWrite {
  playerId: string;
  puzzleId: string;
  familyId: string;
  difficulty: PuzzleDifficulty;
  runId: string;
  resultClass: ResultClass;
  elapsedActiveSeconds: number | null;
  hintsUsed: number;
  incorrectAttempts: number;
  receivedAt: number;
}
```

Stored completion facts and `completionFactsMatch()` include the two new mastery facts. Reusing a run ID with different `hintsUsed` or `incorrectAttempts` is a conflict, not a successful replay.

Exact replay remains idempotent.

Within one existing backend-specific transaction/batch boundary:

1. enforce variant deletion fence and retained-run quota
2. insert/find the completion run and enforce full V2 fact equality
3. for a newly inserted run only, insert the first family+difficulty clear if absent
4. update the eligible mode-specific best time
5. insert factual mastery badges
6. evaluate/insert fixed achievement rows
7. return the durable progression delta

Replace the old Standard-only canonical-best predicate with competitive eligibility for `standard_timed | rotation_timed`; best-time rows remain separated by `result_class`.

## 11. Completion Eligibility

- `standard_timed`: progression + Standard best-time board
- `rotation_timed`: progression + Rotation best-time board
- `assisted_timed`: progression only
- `relaxed`: progression only

Hintless/Flawless can be earned by assisted/relaxed runs when the factual counters satisfy the badge. Rotation Clear requires `rotation_timed`.

Network/submission failure never blocks local puzzle completion.

## 12. Progression Tables

### 12.1 Completion runs

```text
puzzle_completion_runs
  player_id
  run_id
  puzzle_id                variant ID
  result_class
  elapsed_active_seconds   nullable for relaxed
  hints_used
  incorrect_attempts
  completed_at

PRIMARY KEY (player_id, run_id)
```

Keep the current run quota policy and reset `player_completion_usage` with old history during the breaking migration.

### 12.2 Competitive best times

```text
puzzle_best_times
  player_id
  puzzle_id
  result_class             standard_timed | rotation_timed only
  best_time_seconds
  achieved_at

PRIMARY KEY (player_id, puzzle_id, result_class)
```

Index `(puzzle_id, result_class, best_time_seconds, achieved_at)`.

### 12.3 Unique clears

```text
player_difficulty_completions
  player_id
  family_id
  difficulty
  first_completed_at

PRIMARY KEY (player_id, family_id, difficulty)
```

This key implements the award-once rule.

### 12.4 Achievements

```text
player_achievements
  player_id
  achievement_id
  unlocked_at

PRIMARY KEY (player_id, achievement_id)
```

Definitions/points live in code constants.

### 12.5 Mastery

```text
player_variant_mastery
  player_id
  puzzle_id
  badge
  earned_at

PRIMARY KEY (player_id, puzzle_id, badge)
```

Allowed badges: `hintless`, `flawless`, `rotation_clear`.

## 13. Overall Score and Achievement Catalog

Completion points:

| Difficulty | Points |
| --- | ---: |
| Easy | 100 |
| Normal | 200 |
| Hard | 300 |

Each family+difficulty contributes once. Replays contribute zero completion points.

Score is derived:

```text
100 * unique Easy clears
+ 200 * unique Normal clears
+ 300 * unique Hard clears
+ fixed achievement bonuses
```

No score/event ledger or mutable total is stored.

Initial achievements:

| ID | Requirement | Points |
| --- | --- | ---: |
| `first_clear` | Complete any family+difficulty | 25 |
| `getting_started` | Complete 5 unique family+difficulty variants | 50 |
| `puzzle_regular` | Complete 15 unique family+difficulty variants | 100 |
| `full_set` | Complete Easy + Normal + Hard for one family | 75 |
| `hard_mode` | Complete any Hard variant | 50 |
| `hard_veteran` | Complete 5 unique Hard variants | 100 |
| `hintless` | Earn Hintless mastery once | 25 |
| `flawless` | Earn Flawless mastery once | 25 |
| `rotation_clear` | Earn Rotation Clear mastery once | 25 |

Maximum initial achievement bonus is 475, less than one full family clear (600).

Predicates are ordinary code/queries, not a rule interpreter.

## 14. Per-Family Competitive Leaderboards

Every family has Standard and Rotation boards per difficulty.

```text
GET /api/puzzle-families/:familyId/leaderboard
    ?difficulty=normal
    &mode=standard
```

The endpoint resolves family+difficulty to a variant ID, then queries that mode's best-time rows.

Ranking order:

```text
best_time_seconds ASC
achieved_at ASC
player_id ASC
```

One player occupies at most one row per board. Return top 50 plus the signed-in player's own row/rank when outside the top 50. Whole-second timing remains unchanged.

## 15. Overall Leaderboard

```text
GET /api/leaderboard
```

Order:

```text
score DESC
hard_completions DESC
normal_completions DESC
easy_completions DESC
score_reached_at ASC
player_id ASC
```

`score_reached_at` is derived as the latest timestamp among currently contributing unique-clear/achievement rows. Do not store a mutable score timestamp or materialized leaderboard at this scale.

## 16. Profile Summary and Puzzle Results

Dropping `puzzle_stats` must not delete the shipped Profile → Puzzle Results screen.

Rewrite the player results query at **family+difficulty** grain:

```ts
interface PlayerPuzzleResultRow {
  familyId: string;
  familyName: string | null;
  difficulty: PuzzleDifficulty;
  variantId: string;
  standardBestTimeSeconds: number | null;
  rotationBestTimeSeconds: number | null;
  totalCompletions: number;
  firstCompletedAt: number;
  lastCompletedAt: number;
}
```

`totalCompletions` comes from the completion-run ledger for the variant. Bests come from the two `puzzle_best_times` rows.

Preserve the existing bounded cursor-pagination style. For display ordering, timed rows come before rows with no competitive best; use the minimum non-null Standard/Rotation best as the stable sort value, then `variantId` as tie-breaker. This sort is only for the profile list and does not merge the two competitive leaderboard modes.

The profile also shows:

- overall score/rank
- Easy/Normal/Hard unique-clear counts
- achievement progress
- mastery count/progress
- the rewritten Puzzle Results list

## 17. Player Identity and Privacy

interface LeaderboardPlayer {

The current `AdminPuzzlesPanel` becomes family-scoped:

- filter/search/page by family name/category/status
- show one family thumbnail/reference preview
- show Easy/Normal/Hard counts instead of one `pieceCount`

## 20. NativeScript Offline Library

The NativeScript client is now a real second catalog consumer and must cut over in this PR.

Its API becomes family-oriented for browsing:

```text
listPuzzleFamilies() -> GET /api/puzzle-families
familyThumbnailUrl(familyId)
```

The mobile Gallery renders one family with three difficulty download actions. Selecting a difficulty passes that concrete variant ID to the existing download pipeline.

Downloaded packages, downloaded-library rows, save sessions, and gameplay launches remain concrete-variant based. One family may therefore have multiple installed difficulties.

Do not retain `GET /api/puzzles` as a variant-list compatibility endpoint solely for mobile.

This PR does not add mobile account achievements/leaderboard UI; the offline client only needs the family catalog/difficulty cutover so its in-tree API contract stays valid.

## 21. Local Quick Puzzles

Quick Puzzles remain:

```text
image + user-selected piece count -> one local puzzle
```

They do not gain families, fixed tiers, account progression, mastery, or server leaderboards.

Keep their existing uploader/schema/session IDs and `puzzle-progress-q-*` keys.

## 22. Breaking Migration and Cutover

Existing server puzzles may use arbitrary counts such as 192/225 and cannot truthfully be relabeled Hard.

Use one-shot operator tooling; no runtime legacy parser or legacy difficulty.

### 22.1 Pre-deploy export/inventory

Before the destructive D1 migration:

1. enumerate old ready server puzzles
2. capture name/category/aspect ratio/owner/old puzzle ID/piece count
3. download each retained original image
4. fail if any ready puzzle cannot be exported

This is read-only safety/ownership capture. Do **not** purge the live catalog before deployment.

### 22.2 Deploy new family-capable code

Deploy the breaking D1/API/workflow/web/mobile contract. Old `puzzle:*` KV/R2 objects may remain temporarily but new catalog reads ignore them.

The D1 migration intentionally resets:

- old `puzzle_stats`
- old `puzzle_completion_runs`
- `player_completion_usage`

and creates the new family/progression tables. Player profile identity is preserved.

### 22.3 Import replacements

Use the new Access-protected admin family-create endpoint with an explicit operator `ownerId` seam from the export manifest. Each import waits until all three variants are ready.

Import/verify families before deleting old KV/R2 source objects. This avoids destroying the only source image before successful three-tier regeneration.

### 22.4 Cleanup old orphans

After every replacement family is verified ready, a one-shot maintenance script deletes the leftover old `puzzle:<oldId>` KV records and `puzzles/<oldId>/...` R2 objects from the export manifest. This cleanup uses operator/Cloudflare tooling, not a permanent legacy HTTP route.

Do not keep a runtime `legacyPuzzle` branch, V1 parser, old catalog list, or old admin path alias.

## 24. Acceptance Criteria

The feature is complete when:

1. Every server family exposes exactly Easy, Normal, and Hard with the approved counts.
2. `PuzzleSession` remains one fixed concrete variant and has no mutable difficulty.
3. Web/admin/mobile catalog listing is family-scoped; `GET /api/puzzles` is not retained as a list compatibility endpoint.
4. One family Workflow uses difficulty-qualified row/finalize checkpoints and eagerly produces all three variants.
5. Family is the deletion/reaper grain; no variant can be independently reaped/deleted.
6. Shared original/thumbnail are family-owned and piece assets remain variant-owned.
7. Web family cards resolve Continue/progress/local best independently per difficulty/variant.
8. `completionRequestFromSeal()` emits V2 facts and replay equality includes hints/incorrect attempts.
9. Unique Easy/Normal/Hard clears award 100/200/300 once; replay awards zero completion points.
10. The nine achievements unlock once and mastery remains non-scoring.
11. Standard and Rotation have separate family+difficulty top-50 boards.
12. Assisted/relaxed progress but never enter time boards.
13. Overall ranking is derived with the approved tie-breakers.
14. Profile retains a paginated family+difficulty Puzzle Results list with Standard/Rotation bests.
15. Leaderboards reuse display name/avatar and never expose email.
16. Admin remains Access-only and the CLI Access destination is updated to the family endpoint.
17. NativeScript gallery consumes families and downloads concrete variants by difficulty.
18. Quick Puzzles remain arbitrary-count/local and retain their current save keys.
19. Migration is export -> deploy -> import/verify -> cleanup old objects; it does not purge source content first.
20. No second DO, child workflows, score ledger, achievement engine, generic ranking API, runtime V1 parser, old catalog list, or legacy difficulty is introduced.

## 25. Design Rationale

The core KISS boundary is now explicit:

- **family** = catalog/image/workflow/deletion identity
- **variant** = board/session/completion/local-stats/competitive identity

That boundary follows the ownership already present in the code rather than forcing shared family assets through puzzle-scoped cleanup or forcing family concepts into the pure session engine.

Score remains derived from normalized unique-clear and achievement rows, so unique keys enforce the anti-farming rule without another ledger/cache subsystem.

The migration deliberately resets incompatible gameplay history and leaves no permanent legacy semantics. Import-before-cleanup protects the only source images without requiring a long-lived dual catalog implementation.
